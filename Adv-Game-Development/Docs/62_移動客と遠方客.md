# 62 移動客・遠方客（12〜18m固定配置と移動経路）

Issue #62。正本は `Docs/投福神社_企画仕様書_v8_完成版.html` の 6章（救済成功／失敗の演出・笑顔の伝播）・8章（スポーン・空間配置の比率）・10章（参拝客）と付録B（B-1／MOVE.SPEED／PLACEMENT／SPAWN.TYPE.11／EXIT.TIMING）。
このドキュメントは**実装がどの規則に従っているか**を1枚にまとめたもので、数値の正本ではない。
数値を変えるときは付録B（Phase 2 以降は移管先スプレッドシート）を直してから、ここと実装を合わせる。

## 1. 何を直したか

#54 で客種（`CustomerKind`）と数値表（`CustomerKindTable`）はできていたが、TestGame の客（`MockCrowdDirector`）は全員が通常客で、次の穴があった。

| 穴 | 影響 |
|---|---|
| 客種を抽選していない | 移動・遠方・欲張り客が出ない。T2 の4択（確実／二重円／奥を救う／欲張りへ2発）が成立しない |
| 近／中／遠がワールドZ座標（z=27〜33／19〜26／12〜18）で決まっていた | ShootPos（z=38.73）からの実距離は約 7〜27m。**遠方の客が照準の届く 18m より奥**にいた |
| 救済・黒客化した客がその場で消える（0.4秒） | 帰路が無いので、笑顔の伝播（#56）の「すれ違い」が起きない |

## 2. 客種の抽選（正本：v8 10章「出現比率」「同時上限」／付録B SPAWN.TYPE.11）

`CustomerKindPicker`。補充が必要になった瞬間に1回だけ抽選する。

| 規則 | 実装 |
|---|---|
| 比率 | `MockCrowdDirector.kindWeights`。既定は4種がすべて出る11月（通常45／移動30／遠方15／欲張り10／ボス0） |
| 同時上限 | 欲張り客2人・ボス客1人に達した客種は抽選から外し、残りを100%へ再正規化 |
| 数値 | 抽選した客種で `CustomerState.Setup(kind, CustomerKindTable)` を呼び、初期R・基礎点・評価（付録B B-1）を差し込む |
| 分類ログ | `CustomerSpawnId.Category` に客種名（`Normal`／`Moving`／`Distant`／`Greedy`）を入れる。#63 の T2 選択分布にそのまま出る |

解禁スケジュール（0:38 欲張り／0:48 遠方／1:00 移動）による比率の切り替えは #57 の担当。ここは1組の比率を持つだけ。

## 3. 距離帯と配置（正本：v8 8章「空間配置の比率」／付録B PLACEMENT）

`PlacementBands` と `MockCrowdDirector`（`bandSpace = DistanceFromOrigin`）。

- **距離の基準点**は照準の origin（`ShootPos`）。水平距離で 近3〜7／中7〜12／遠12〜18m。照準（#60）の届く範囲 3〜18m と一致する。
- 左右は `xRange`（見えない壁の内側）と `maxLateralAngle`（既定40°）の両方に収め、奥行きはカメラの向く -Z 方向に取る。
- 比率 40／40／20% は**定位置にいる非黒客の目標占有率**。現在の目標体数を最大剰余法で整数枠に丸め（15人なら 6／6／3）、補充時は不足率（(枠−占有) ÷ 枠）が最大の帯を選ぶ。同率なら手前。
- **遠方客は必ず遠**。遠に空きがないときだけ次に不足する帯へ回し、そのときの占有を Console に残す。
- 遠の占有には通常・移動・欲張り客も入る（遠方15% は客種の抽選率、遠20% は全客種の占有率で、別の数字）。

TestGame の画面に収まるかは Unity 上で `Camera.WorldToViewportPoint` で確かめた（カメラ (0,5.3,39)・俯角31.7°・FOV75、16:9）。

| 距離 | 足元の高さ（画面下から） | 頭の高さ |
|---|---|---|
| 3m | 17% | 34% |
| 7m | 45% | 58% |
| 12m | 60% | 70% |
| 18m | 68% | 76% |

## 4. 移動客の往復（正本：v8 10章「移動客」／付録B MOVE.SPEED）

`PatrolPath` と `CustomerMotion`。

- 定位置に着いてから、定位置を中心に**左右3m（端から端。中心から±1.5m）**を往復する。奥行き（Z）は変えない。
- 速度は `MockCrowdDirector.movingSpeed`（既定 1.0m/s）。**実行中に Inspector で変えると、歩いている移動客にも次のフレームから反映**する（T2 の変数変更テスト用）。
- 経路が帯の左右範囲からはみ出さないよう、中心を内側へ寄せる。
- 往復の経路とほかの客が歩いて重ならないよう、定位置は間隔を満たす候補から選ぶ。
  - どちらかが移動客なら、往復の経路全体で測って `movingLaneClearance`（1.2m＝体の直径1m＋余裕）以上
  - どちらも立っている客なら、従来どおり `minSlotDistance`（2.2m）以上
  - 選んだ帯に候補が無ければ、候補がある帯のうち不足率が最大の帯へ回す（遠方客は遠から動かさない）。それも無ければ、選んだ帯でいちばん余裕のある候補
- 歩き出す向きは「客ID × 用途（`PlaytestStreams.Motion`）」の固定シードで決める。位置は歩いた道のりだけで決まるので、同じシード・同じ速度なら同じ経路をたどる。

## 5. 退場経路と、移動客が救済・黒客化したとき（正本：v8 6章）

| 出来事 | 扱い |
|---|---|
| 救済（R=0） | その場で往復をやめ、**3秒**かけて出口まで歩く。当たり判定は消える |
| 黒客化（D=100） | その場で往復をやめ、**4秒**かけて出口まで歩く。当たり判定は残る（邪魔になる） |
| 入場の歩行中に救済・黒客化 | 退場経路が入場歩行より優先する（位置は LateUpdate で書く） |
| 退場中 | rescued／black は終端なので往復へは戻らない |
| 定位置 | 救済・黒客化の**瞬間に空ける**（6章「退場開始と同時に枠を空ける」「黒客化した瞬間に上限から外れる」）。補充は退場を待たない |

- 出口は手前（プレイヤー側）の左右 `exitPoints`（既定 (±9, 1, 37)）。客は左右位置が近い方の出口へまっすぐ歩く。
- 奥の客ほど帰路が長く、手前の客の間を通り抜けるので、すれ違う人数が増える（6章「参道の奥にいる参拝客ほど、すれ違う人数が多くなる」／7章 遠方客「帰路が長く伝播人数が多い」）。
- 歩く時間は退場秒数で固定なので、帰路が長い客ほど速く歩く。
- 伝播そのもの（接触判定・有向ペア1回・最大4人・+20）は #56 の担当。ここは経路だけを用意する。

## 6. コインプッシャー（#35）との関係

`Customer_Move` は Rigidbody の速度を毎 FixedUpdate 上書きして +Z へ押し続ける。往復・退場歩行は transform を直接動かすので両立しない。

- TestGame の客プレハブ Variant は、以前から `Customer_Move` を無効化し Rigidbody を kinematic にしてある（`ApplyVisibilityMockToTestGame`）。
- 念のため `CustomerMotion` も、動かし始めるときに `Customer_Move` が有効なら止め（Console に警告）、Rigidbody を kinematic にする。
- 近い帯（正面 約3.7〜4.7m）は、コインプッシャー用の見えない前壁 `Wall/Cube (2)`（z=34.0〜35.0）と重なる。客は kinematic なので押し戻されず、壁も描画されない。

## 7. 既存シーンへの影響

追加した機能はすべて `MockCrowdDirector` のスイッチで、既定は OFF。

| スイッチ | TestGame | VisibilityMock（#44）／UsbGateTest（#52） |
|---|---|---|
| `assignKinds` | ON | OFF（全員通常客のまま） |
| `bandSpace` | DistanceFromOrigin | WorldZ（従来の zRange） |
| `occupancyShare` | 40／40／20 | 0（帯を問わず空きから選ぶ） |
| `exitWalk` | ON | OFF（その場で消える） |

スイッチによらず変わるのは「救済・黒客化の瞬間に定位置を空ける」だけ。退場中の体は `Members` に残るので、#52 の描画体数・退場中の数の数え方は変わらない。

TestGame の設定は `Toufuku/Mock/Apply Visibility Mock to TestGame` で入る（何度実行しても同じ状態になる）。

## 9. 確認したこと

- Unity のコンパイルエラー 0 件。EditMode テスト **426 件すべて成功**（新規 3 ファイル。既存テストの回帰なし）
- PlayMode（TestGame、計測シード 42、入力なし。救済・黒客化はスクリプトから `ApplyCorrectColorHit` / `SetDangerForDebug` で起こした）

| 完了条件 | 結果 |
|---|---|
| 4種がすべて出現する | 1回目のプレイで出現した客：通常7／移動10／遠方6／欲張り3（ほかに黒札8） |
| 基礎点と評価値が得点表どおり | `CustomerState` から読み出して 通常 100・+10／−20、移動 150・+10／−20、遠方 200・+15／−30。欲張り客は出現だけ確認（値は同じ数値表から読む） |
| 遠方客が 12〜18m に配置される | 遠方客の距離 15.1／15.6／16.5m。帯の占有は 近5/6・中5/6・遠2/3（目標15人、黒札3人を除く） |
| 移動客の速度を Inspector から変更できる | 実行中に `MockCrowdDirector.MovingSpeed` を 1.0 → 3.0 → 1.0 と変え、歩いた道のりから **1.000／3.008／1.003 m/s** |
| 救済・黒客化しても経路が破綻しない | 往復中の移動客を黒客化 → その場から4秒で出口 (−9,1,37) まで 5.9m 歩いて消滅。遠方客は救済から3秒で 15.9m、近い通常客は 8.8m 歩いて消滅。定位置は救済・黒客化の瞬間に空き（3人救済で 15 → 12）、補充が始まった |
| 往復が他の客と重ならない | 移動客が同時に最大8人往復する状態を約30秒（3965フレーム）監視し、体の中心間距離 1m 未満は 0 回（最小 1.53m） |
| 固定シードで同じ配置・同じ経路が再現される | TestGame のディレクタでシード 42 の15体を2回作り、客種・帯・座標（小数3桁）・往復の中心・歩き出す向きがすべて一致。シード 43 では別の配置 |

途中で見つけて直したもの：1回目のプレイで、近い帯の移動客2人の往復の経路が奥行き 0.25m 差で重なっていた。
近い帯は狭く、立っている客どうしの間隔（2.2m）を往復の経路にも求めると候補が無くなり、「いちばん離れた候補」に落ちていたため。
往復の経路には体の直径＋余裕の `movingLaneClearance`（1.2m）を使い、選んだ帯に候補が無ければ候補のある帯のうち不足率が最大の帯へ回すようにした（上の監視結果は修正後）。

未確認：

- 実機（ESP32）での照準・命中と、動いている移動客への当てやすさ
- 目視での輪郭の読みやすさ（遠方客と通常客が同等か）。スクリーンショット上は 18m の客も輪郭色が判別できるが、展示モニターでの確認はしていない
- 15人＋退場歩行中の体を含めた fps

## 10. レビューで見てほしいこと・未決事項

1. **退場の出口（企画に確認したい）**：手前の左右 (±9, 1, 37) に置いた。帰路は奥ほど長い（遠 15.9m／近 8.8m）が、今回の1回では 1m 以内ですれ違った active 客は遠方客 1人・近い客 2人で、**「奥ほど多くすれ違う」にはなっていない**。出口へ直進すると帯の端を通るため。笑顔の伝播（#56）を入れるときに、参道の中央を通る経由点を足すかを決めたい
2. **「左右3m」の解釈**：端から端 3m（中心から ±1.5m）とした。中心から ±3m なら `movingPatrolWidth` を 6 にする
3. **同時上限の扱い**：10章に「未解禁・同時上限到達の種類を除外して再正規化」と「上限時は通常客へ置換する」の2通りの記述がある。前者で実装した
4. **D満タン秒数**：TestGame の客プレハブ Variant には視認性モック（#44）の上書き 66.7秒が残っているので、TestGame では客種ごとの D満タン秒数（移動20／遠方22／欲張り28秒）が効かない。R・基礎点・評価は表どおり。本番値に戻すかは #57（時間割）と合わせて決めたい
5. **入場中の D**：客プレハブが `startActive = ON` なので、入場の歩行中から D が進み弾も当たる（6章では入場中は D 停止・当たり判定なし）。#54 以前からの挙動で、今回は触っていない
6. **欲張り客**：R=2・基礎点300 が入るところまで。2色目への輪郭の切り替えと頭上ゲージの表示制限は別 Issue
7. **コインプッシャーの前壁**：近い帯（正面 3.7〜4.7m）が #35 の見えない壁 `Wall/Cube (2)` と重なる。客は kinematic なので挙動に影響しないが、壁を残すかは淡路さんに確認したい
8. **近い帯の見え方**：3〜7m の客はかなり大きく映る。T1 の前に近／中／遠が読み分けられるかを目視で確認してほしい
