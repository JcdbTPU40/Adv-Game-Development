# 54 危険度D／残り必要発数R の状態遷移

Issue #54（v8変更点1・2）。正本は `Docs/投福神社_企画仕様書_v8_完成版.html` の 6章と付録B B-1。
このドキュメントは**実装がどの表に従っているか**を1枚にまとめたもので、数値の正本ではない。
数値を変えるときは付録B（Phase 2以降は移管先スプレッドシート）を直してから、ここと実装を合わせる。

## 1. なぜ2変数に分けたか

v7 までは「不満ゲージ1本」で救済も時間切れも表していたため、

- 初期値や命中時の削り量しだいで、複数発客が想定より早く救済されてしまう
- 誤色でもゲージが削れるので、無限弾で誤色を連打すると黒客化を遅らせられる

という2つの実装分岐・抜け道があった。v8 では

| 変数 | 意味 | 範囲 | 動かすもの |
|---|---|---|---|
| 危険度 D | 残り時間 | 0〜100 | active 中の時間経過（増）／笑顔の伝播（−5） |
| 残り必要発数 R | 救済までの手数 | 1〜3 | 正色命中（−1） |

に分離し、**互いに干渉させない**。誤色は D も R も動かさない。

## 2. 状態遷移表（正本：v8 6章）

| 状態／出来事 | 危険度 D | 残り必要発数 R | 次状態 |
|---|---|---|---|
| 参道を歩いて入場中 | 0 で停止 | 客種ごとの初期値（1／2／3） | 予告中（Entering）。当たり判定・二重円・危険度進行なし |
| 定位置へ到着 | 0 から開始 | 維持 | active |
| active 中の時間経過 | `D += 100 × 経過秒 ÷ 満タン秒数` | 変化なし | active（D は 0〜100 に制限） |
| 現在要求中の正しい色が命中 | 変化なし | R を1減らす | R>0 なら active 継続、R=0 なら rescued |
| 違う色が命中 | 変化なし | 変化なし | active 継続。誤投擲フィードバック＋福の連なり C とご加護進捗 G のリセット |
| 笑顔が伝播 | `max(0, D−5)` | 変化なし | active 継続 |
| D が 100 に到達 | 100 | 以後使用しない | black（黒客化）。救済へ戻らない |

rescued／black は終端状態。退場中に再び active へ戻さない。

### 同じイベント時刻の解決順

> 正色着弾と有効な笑顔伝播を先に解決 → R と D を更新 → R=0 の救済判定 → なお active で D≥100 なら黒客化

実装では、

- `CustomerState.Update` … `CustomerStateMachine.TickDanger()` で D を進めるだけ（ここでは黒客化しない）
- `CustomerState.LateUpdate` … `CustomerStateMachine.ResolveBlackout()` で D≥100 の黒客化を確定

とすることでこの順序を保証している。フレーム内に着弾した正色命中・笑顔の伝播は LateUpdate より前に解決されるため、
**間一髪の救済が一意に優先される**（D がちょうど 100 に達したフレームの命中は救済になる）。

## 3. 客種ごとの数値（付録B B-1 ＝ `CustomerKindTable`）

| 客種 | 初期R | D が 100 になる秒数 | 救済完了の基礎点 | 評価(成功) | 評価(失敗) |
|---|---|---|---|---|---|
| 通常客 | 1 | 15〜25 | 100 | +10 | −20 |
| 移動客 | 1 | 20 | 150 | +10 | −20 |
| 遠方客 | 1 | 22 | 200 | +15 | −30 |
| 欲張り客 | 2 | 28 | 300 | +15 | −20 |
| ボス客 | 3 | 30 | 500 | +25 | −30 |

- 全員 D=0 で開始し、定位置到着後に D だけが時間で増える。
- 通常客の満タン秒数（15〜25秒）は、`PlaytestRandom` の「客ID × 用途(DangerSeconds)」の固定シードで引く（#63 の再現性を保つ）。
  スポナーが `CustomerState.Setup(客種, 数値表, 乱数)` を呼ばない場合は幅の中央値（通常客なら20秒）になる。
- 検証シーン用に `CustomerState.dangerFullSecondsOverride`（0 なら不使用）がある。視認性モック(#44)はこれで 66.7 秒に伸ばし、
  12〜15体を並べた状態を保つ。本番の客プレハブは 0 のままにする。
- 得点は**救済完了時に1回だけ**。欲張り客の R=2→1 は 0 点、R=0 の救済完了で 300 点（＋最終弾の命中精度）を確定する。

## 5. 誤色と黒客の扱い（抜け道を塞ぐ）

- 誤色命中：D も R も変わらない。福の連なり C とご加護進捗 G だけを 0 に戻す（付録B `STATE.WRONG` = 0 / 0 / 0へ / 0へ）。
  現在の実装ではご加護 G は福の連なりから導かれているため、C のリセットで G の進捗も同時に切れる。
- 黒客の当たり判定は**残す**（v8 6章「失敗時：当たり判定 残る（邪魔になる）」）。
  黒客への通常弾は縁が入らず、福の連なりだけが途切れる。
- 黒客は**笑顔の伝播の対象外**（`CustomerStateMachine.IsRescueTarget` が false）。
  黒客を対象に含めると「黒客が多いほど縁が増える」抜け道になるため、優先救済（二重円）の候補集合からも同じ述語で外している。
- 救済成功時は当たり判定を消す（救済済みの客に当て続けて縁を稼ぐ抜け道を塞ぐ）。

## 7. 手元での確認手順（PlayMode）

1. `Assets/Members/Jungaya/Scenes/TestGame.unity` を開く。
2. 客プレハブ（`Assets/Members/Jungaya/Prefabs/Customer.prefab`）の `CustomerState` には
   `CustomerKindTable`（`Assets/Members/Jungaya/Scripts/Rescue/CustomerKindTable.asset`）が割り当て済み。
   `客種` を切り替えるだけで初期R・D満タン秒数・基礎点が変わる（数値表 未割り当てでも通常客相当のフォールバック値で動く）。
3. 確認する挙動:
   - 何もしないと足元の表示（現状は頭上バー）が満ちて黒客化し、以後救済できない。
   - 違う色を連打しても黒客化までの時間が変わらない（ログ `[State]` に R の変化が出ない）。
   - 欲張り客（初期R=2）は1発目で連なりだけ伸びて縁が増えず、2発目で 300 点＋精度ボーナスが1回入る。
   - 救済済みの客には弾が当たらない（すり抜けて外し扱い）。黒客には当たり、連なりが切れる。

## 8. この Issue に含めなかったもの（申し送り）

- **笑顔の伝播そのもの**（退場歩行中の交差判定・縁+20・上限4人・倍率スナップショット）は別Issue。
  #54 では受け手側の条件（`IsRescueTarget`）と D−5 の適用だけを用意した。
- **優先救済 +50**（二重円の対象へのボーナス加点）は #55 の担当。候補集合の条件だけ本Issueで合わせた。
- **黒客ヒットの評価 −15** と評価値レンジ 0〜300（付録B RANK.VALUE）は評価まわりのIssueで扱う。
  現状の `ShrineRating` は 0〜100 のまま、増減だけ客種ごとの値（B-1）を使うようにした。
- **客種の抽選比率**（通常75% / 移動6.25% / 遠方9.375% / 欲張り9.375% など）は #57 / #62。
  本Issueのスポナーは客種を1つ固定で生成する。
- **足元円＝D／頭上ゲージ＝R の本番表示**（UI.DANGER の D=50 表示開始・D=85 脈打ち）は表示側のIssue。
  検証用の `CustomerGaugeHud` は D のバーと R の目盛り（R≧2 のみ）を暫定表示する。
