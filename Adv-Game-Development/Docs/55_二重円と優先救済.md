# 55 二重円と優先救済（SwingAccepted 時点の対象IDで +50 確定）

Issue #55（v8 変更点4）。正本は `Docs/投福神社_企画仕様書_v8_完成版.html` の 6章・7章と付録B（B-2／UI.DANGER／PRIORITY.MARK）。
このドキュメントは**実装がどの規則に従っているか**を1枚にまとめたもので、数値の正本ではない。
数値を変えるときは付録B（Phase 2 以降は移管先スプレッドシート）を直してから、ここと実装を合わせる。

## 1. 何を直したか

v7 までは「その時いちばん危険な1人」を二重円で示すだけだった。弾の飛翔は 0.25〜0.65 秒あるので、

- 二重円を見て投げた → 飛んでいる間に他の客の D が上がって二重円が移る → 表示どおり狙ったのに +50 が入らない

という、**画面を読んだ判断が無効になる**穴があった。v8 では次の 2 つを固定する。

| 固定するもの | どこで | 効果 |
|---|---|---|
| 候補集合と同値順 | `PriorityTarget` / `PriorityRescue` | 同じ D の客が何人いても二重円が 1 人に定まる。フレームごとに移らない |
| 発射時点の対象ID | `OmamoriProjectile.PriorityTargetId` | 飛翔中に二重円が移っても、その弾の +50 の判定は変わらない |

優先救済に閾値はない（付録B PRIORITY.MARK：対象数 1 人／D 閾値なし）。
D が低いうちに救っても +50 は入るので、「D を上げてから救うと得」という**待って稼ぐ攻略は構造的に存在しない**（v8 7章の経緯）。

## 2. 候補集合と同値順（正本：v8 6章「最危険マーク＝優先救済候補」／7章 得点表）

**候補集合**：画面内にいる、`active` かつ 未救済・非黒客・R>0 の客だけ。
入場中（参道を歩いている）・退場中の救済客・黒客は入れない。黒客を残すと「黒客が多いほど縁が増える」抜け道になる。

**同値順**：上から順に見て、差が付いた時点で決まる。

| 順位 | 条件 | 理由 |
|---|---|---|
| 1 | 危険度 D が大きい | 「いちばん危ういひとり」を示すのが二重円の意味 |
| 2 | 距離が**遠い** | 同じ危険度なら当てにくい方を読ませる（v8 7章の選択の設計） |
| 3 | active になった時刻が**早い** | 先に待っていた客を優先する |
| 4 | 生成IDが小さい | 重複しない値なので、ここまで来れば必ず 1 人に決まる |

D と距離は誤差（`DangerEpsilon` / `DistanceEpsilon` = 1e-3）を挟んで比較する。
歩いている客の距離が毎フレーム 0.1mm 単位で揺れても、二重円がちらちら移らないようにするため。

## 3. 足元の円（正本：付録B UI.DANGER／PRIORITY.MARK）

| 円 | 出る条件 | 動き |
|---|---|---|
| 危険円（赤系） | D ≥ 50。D が上がるほど濃く・太く | D ≥ 85 で**明るさ**が脈打つ |
| 二重円（金系） | その時の優先対象 1 人。**D < 50 でも出す** | ゆっくり**半径**が呼吸する |

- 脈打ちの軸を分けてある（危険円＝明るさ／二重円＝半径）。同じ軸で動かすと 2 つの意味が混ざって読めなくなる。
- 色は赤系と金系に固定する。輪郭＝種類／足元＝危険度／頭上＝残り発数 のチャネル分離（v8 6章）を崩さないため、
  お守りの 5 色とは別系統にしている。
- 待機列から見える必要がある（13章 観戦要件）ので、線幅はカメラからの距離で割り増しする
  （`widthReferenceDistance` より遠いと距離に比例。上限 `maxWidthScale`）。遠くの客で線が消えない。
- 見た目の調整は `GroundRingDirector`（シーンに 1 つ）に集約した。T1 の「初見で読めるか」はここだけを触る。

## 4. +50 が入るまでの流れ（正本：v8 4章「通常弾」／7章 縁の計算式）

```
SwingAccepted（有効スイング確定）
  └ OnusaThrower : 色・着弾目標点と同時に PriorityRescue.CurrentTargetIdOrNone を弾へ保存
       └ OmamoriProjectile.PriorityTargetId （この値は飛翔中いっさい変えない）
飛翔 0.25〜0.65 秒（この間に二重円が別の客へ移ってもよい）
  └ 着弾 : OmamoriHitResolver.ApplyHit(..., priorityTargetId)
       ├ CustomerRescue → CustomerState : 正色なら R を1減らす。R=0 なら救済完了
       ├ PriorityRescue.IsBonusHit(保存ID, 当たった客のID, 救済完了したか)
       └ ScoreManager.RegisterCorrectHit(zone, rescued, 基礎点, priorityRescue)
            縁 = round((基礎点 + 命中精度加点 + 優先救済加点) × 福の連なり倍率 × ご加護倍率)
```

- 加点が入るのは**救済完了させた弾だけ**。欲張り客の1発目・ボス客の1〜2発目は 0 点（付録B B-2「部分点なし」）。
- 照合は生成ID（`CustomerSpawnId`）で行う。参照ではなく ID なので、客が退場・破棄されても誤爆しない。
- 二重円の表示・発射時の保存・計測ログ（#63）の `priority_target_id` は、すべて `PriorityRescue` の同じ 1 か所を見る。
  画面で光っている客と、加点対象の客と、ログの値が食い違わない。

## 5. 数値の出どころと「+50 → +30」の下げ方

付録B B-2 の加点は `ScoreBonusTable`（ScriptableObject）に写してある。
実体は `Assets/Members/Jungaya/Scripts/Scoring/ScoreBonusTable.asset`。`ScoreManager` に割り当てて使う。

| 項目 | 既定 | 備考 |
|---|---|---|
| 命中精度：中心 / 中間 / 外周 | +50 / +20 / +0 | #60 |
| 優先救済 | **+50** | T2 で「二重円だけを追う」が支配戦略なら **+30** へ |

T2 の結果で下げるときの手順（**コードは触らない**）:

1. 付録B B-2 の値を +30 に直す（Phase 1 は HTML が正本）。
2. `ScoreBonusTable.asset` の `優先救済` を 30 にする。
3. このドキュメントの表と、17章のテスト記録に判定した T2 のテストIDを残す。

数値表を割り当てていないシーンでは `ScoreManager` のフォールバック値（付録B と同じ既定値）が使われる。

### 7-2 PlayMode（手で確認する）

`Toufuku/Rescue/Build Priority Rescue Scene` でシーンを作り、`Assets/Members/Jungaya/Scenes/PriorityRescueTest.unity` を Play する。
操作は 1 キーで色（健康）を選び、クリックで振る。

| キー | 場面 | 見るところ |
|---|---|---|
| F5 | 同値ケース | 同じ D・同じ距離の客が 3 人。二重円が 1 人だけに出て、**移らない**こと |
| F6 | 移動ケース | 投げた直後に別の客の D が跳ね上がり、二重円がその客へ移る。それでも狙った客を救済すれば HUD の「優先救済の加点」に +50 が出ること |
| F7 | 通常 | D が時間で増える。D=50 で危険円が出て、85 から脈打つこと |
| F8 | 客を作り直す | 何度でも同じ配置でやり直せる |

HUD には「発射時に弾へ保存した二重円ID」「着弾時の二重円ID」「優先救済の加点」が出る。
移動ケースでは 2 つの ID が違う値になり、それでも加点が入る——これが #55 の完了条件そのもの。

## 8. 積み残し・注意

- **物理衝突の弾**（`OmamoriBullet` / `TestShooter`）は優先対象IDを持たないので +50 が入らない。
  本番の経路は `OnusaThrower` → `OmamoriProjectile`（#60）なので実害はないが、確認シーンで
  TestShooter を使うと加点が出ない点に注意する。
- **大祓（追加T5）** は仕様どおり優先救済を乗せない（付録B「大祓は基礎点だけを ×1.0」）。実装時もここを通さない。
- **計測ログの列は増やしていない**。`priority_target_id`（発射時）と `target_id`（当たった客）の一致で T2 の
  `choice.priority_share` は今までどおり出せる。実際に +50 が入ったかを列に足すかは T2 の集計方針が決まってから。
- 二重円の**色・太さの最終値は T1 待ち**。初見の子どもが「薄い赤の円と重なっても 1 人だけ」と読めるかを見て、
  `GroundRingDirector` の設定を詰める（v8 13章の承認待ち項目）。
